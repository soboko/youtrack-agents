# YA-10: voice client

Issue: YA-10. Director: Claude Opus 5. Baseline: YA-8's contract commit `5b8f0cc` on `codex/director-ya8` (this
branch, `claude/director-ya10`, is based on it and must be rebased when YA-8 merges).

A voice client for the tracker, driven entirely by speech, for a household member who is blind and uses a voice
assistant as their primary computing interface. Not tied to one assistant: the assistant is an adapter, the
conversation core is the product. The issue description is the design brief; this packet is the plan for building it.

## Architecture

```
adapter (text | alexa | phone)        builds VoiceRequest; renders VoiceResponse; resolves the speaker's own tracker
      |  VoiceRequest {input, speaker{userId, evidence[]}, locale, capabilities, requestId}
CONVERSATION CORE                     intents, grammar, working set, paging, verbosity, gating, all wording
      |  VoiceTracker (narrow)        --binding (YA-15)-->  YA-8 TrackerPort  -->  YouTrack (later: Jira)
      |  UserStateStore (opaque)
      |  VoiceResponse {segments[], earcon?, listen, reprompt?, card?, ratePercent}
adapter renders: plain text | SSML + sound library | call TTS
```

The contract is `src/voice/core/types.ts`. It is Director-owned: builders import it and never edit it, and a change
needs a coordination comment on YA-10 first. Decisions it fixes:

- **Evidence, not a score.** The adapter reports what it knows (`person`, `account`, `caller-id`, `keypad-pin`,
  `none`), and `VoicePolicy` lists which kinds each class of action accepts. A voice profile and a caller id are
  different kinds of weak; ordering them would invent a comparison that does not exist.
- **Two input shapes, one intent set.** Alexa resolves intents itself and sends `IntentInput`; text and telephony send
  `UtteranceInput`, and the core's grammar maps it to the same `IntentName`s. The core owns the intent catalogue, and
  the Alexa interaction model is generated from it, so the two cannot drift.
- **Segments, not a string.** Responses are speech segments with pauses. Each adapter renders them in its own medium:
  plain text, SSML breaks, or call TTS. The core never emits SSML.
- **Per-person state is opaque to adapters.** `UserStateStore` stores a string. The core owns and versions the shape:
  working set, focus and reading offset, last response, pending confirmation, preferences. So a DynamoDB or file
  store never has to follow schema changes.
- **The tracker is already the speaker's own.** The adapter resolves a per-user tracker from the linked credential
  before calling the core, which never sees a token. There is no single service token.
- **Logs leave the house.** Content and speech are logged at `debug` only. Intents, counts, timings and failure kinds
  are logged at `info`. The logging is verbose and levelled, but the content stays private.
- **Pure enough to test by transcript.** `converse(request, deps)` depends only on its ports and an injected clock,
  with no platform object and no network. A transcript file (`> utterance` / `< expected speech`) is a complete test.
  It is also how wording gets iterated with the household.

## Conversation design rules the core must satisfy

These come from the issue; the builder turns each one into a transcript test.

1. **Ordinals, not ids.** A query reads a numbered page ("You have 7. One: ..."), and later turns refer to positions.
   The working set persists per person across sessions and expires after `workingSetTtlMs`. After that, an ordinal is
   refused with the way back ("That list has expired. Say 'my issues' to hear it again."), never guessed. Ordinals map
   to the keys captured when the list was read, and the issue is re-fetched when opened.
2. **Fuzzy summary match second, spelled id last.** Spelled ids accept letters, digits and the phonetic alphabet.
3. **Brief by default.** Paging stays below `maxSpeechChars`, with at most five items per page when brief. "More"
   continues; "previous" goes back.
4. **Rigid phrasing.** The same shape of sentence for the same kind of answer, in one module, so it can be learned and
   half-listened to. Numbers come before summaries, and the count comes before the list.
5. **Orientation and recovery.** "Where am I" names the list, the issue and the part. "Repeat" replays the last
   response. After barge-in or a closed session, the next turn resumes from the stored offset.
6. **Markdown is made speakable.** No backticks, table pipes, raw URLs or ids read out. Links become their text,
   tables become "a table of N rows", and code blocks become "a code block". Long descriptions are read a paragraph
   at a time.
7. **Honest counts.** `complete: false` is spoken ("at least 50"), never as "all".
8. **Gating.** Below `readAccepts` the core refuses to read content. It says why without saying what exists, never
   names the tracker's contents, and never falls back to "check the app".
9. **Confirm by summary, never by number** (stage 3). Destructive, bulk and other-people's-work actions are not
   voice-reachable at all.
10. **No secret is ever spoken**, and no spoken PIN. Telephony's second factor is a keypad PIN, entered off-air.

## Risks and decisions log

- [DECISION] Alexa first, telephony second, personal use: owner, 2026-09-12.
- [DECISION] The skill endpoint is AWS Lambda in the owner's AWS account: owner, 2026-09-12. YA-14 therefore
  delivers a Lambda handler, a DynamoDB (or equivalent) `UserStateStore`, least-privilege IAM, and a runbook. The
  skill itself is registered in the Alexa developer console, which is separate from AWS (the same Amazon login can
  own both). Creating the resources is Owner operates, and nothing is deployed without asking.
- [DECISION] Evidence kinds instead of a confidence score, and accepted-kinds policy instead of an ordering.
- [DECISION] The core owns the intent catalogue; the Alexa model is generated from it.
- [ASSUMPTION] "A different account" means a separate login on the same YouTrack instance. It changes only
  configuration, not code.
- [RESOLVED] Account linking: YouTrack 2026.2+ OAuth clients support the authorization code grant with refresh
  tokens (see Platform findings). Creating the client is Owner operates.
- [RESOLVED 2026-09-13] Alexa+ compatibility. The development-stage hello-world skill answers on the household
  Echo and in the Alexa app (Lambda logs 16:26Z and 16:27Z) **with Alexa+ on** (owner confirmed). The first attempts, refused with "not supported on this
  device", most likely failed on the invocation name "my tracker", which collides with Alexa's built-in tracking,
  and/or on propagation delay after enabling; they were not blocked by Alexa+ itself. Invocation names avoid
  everyday Alexa words. Wait a few minutes after enabling or rebuilding before judging a device test.
- [RISK] Voice profiles may not be set up in the household, or may not work for this user. With `readAccepts`
  including only `person`, the skill would refuse everything. The default for personal use is an Owner decision
  before the first live trial. Settled as Option B for reads in this household (see "Owner decision OD1").
- [RISK] The owner cannot judge a screen-reader-grade voice UI by reading it, and neither can an agent. Wording will
  change after the first trial, which is why every string lives in one module and every behaviour has a transcript.
- [RISK] YA-8 is mid-flight. `src/tracker.ts` may change. The voice core depends only on its own `VoiceTracker`,
  so a change there costs YA-15, not YA-13.

## Contract revision 1 (2026-09-12, after review)

Four additions to `src/voice/core/types.ts`, one commit, from the YA-13 and YA-14 reviews:

- `VoiceRequest.timeZone?` (IANA). Without it the core speaks absolute dates only (YA-13 review: UTC days made
  "today" wrong every evening).
- `AdapterCapabilities.maxSpeechChars` documented as plain characters the adapter can deliver whole, markup headroom
  included (YA-14 judge B2: escaping pushed SSML past Alexa's 8000 characters and pieces went silent).
- `UserStateStore` is versioned: `load` returns `{serialized, version}`, `save` takes `expectedVersion` and returns
  `false` on conflict. The core does not retry (YA-13 review, YA-14 judge J7: a late turn overwrote a newer one).
- `ConversationDeps.signal?`, the turn deadline. Optional now, **required before YA-17 ships** (judge B1/D1).

## Platform findings

Checked against vendor documentation on 2026-09-12, with page dates. Only what changes the plan is listed here.

- **Alexa custom skills: still supported.** Nothing on Amazon's deprecation page touches custom skills, account
  linking or personalization (page of 2026-08-17). A **development-stage skill works on Echo devices signed in to the
  developer account with no certification**, and a beta reaches other accounts (up to 500 testers, 90 days each).
  That fits personal use.
- **Alexa+ is the open risk.** Skills stayed on the original Alexa at the Alexa+ launch. Running a skill directly
  on Alexa+ needed Amazon's approval by form, and today's behaviour for an existing custom skill on an Alexa+
  household is UNCONFIRMED. So the first live step on YA-14 is a hello-world skill on the household's own device,
  before the full adapter is deployed.
- **Speaker identity: `context.System.person.personId`.** Present only when the speaker is recognised and has
  "Personalize skills" turned on. It needs the `alexa::person_id:read` permission and a privacy-policy URL, and
  Amazon states it is not authentication. It maps to `person` evidence, and to nothing more. Each recognised person
  can carry their own linked `accessToken`, which suits "a separate account" exactly.
- **AMAZON.SearchQuery** still cannot share a sample phrasing with another slot, and needs a carrier phrase. Hence
  `SlotKind 'phrase'`.
- **YouTrack OAuth: easier than the issue assumed.** Since 2026.2, an admin creates OAuth clients inside YouTrack
  (Administration > Access Management > OAuth Clients), with authorization code plus optional PKCE, and a refresh
  token with `access_type=offline`. No Hub service registration, no permanent token. This retires the account-linking
  risk below to a configuration step (Owner operates).
- **YouTrack also has a built-in remote MCP server** at `/mcp`. Not used: the conversation core is deterministic and
  transcript-tested by design. Recorded as an option if an LLM layer is ever wanted.
- **Google:** Conversational Actions shut down on 2023-06-13. App Actions docs remain, with no stated Gemini support,
  and AppFunctions is an invite-only preview. **No Google adapter is planned.**
- **Siri:** App Intents inside an iOS app only; voice-only dialogs on AirPods are described at WWDC26, and HomePod is
  unconfirmed. A later adapter at most.
- **Home Assistant Assist:** fully local, custom sentences, LLM agents. **No speaker identification in core** (the
  proposal was closed 2025-11-09), so evidence would come from which satellite heard the request. A candidate third
  adapter.
- **Telephony:** Twilio `<Gather input="speech">` and ConversationRelay are both current. STIR/SHAKEN attestation is
  a hint that the caller may use the number, not an identity, which confirms `caller-id` as weak evidence. The
  second factor stays a keypad PIN: never a spoken PIN, per the issue.
